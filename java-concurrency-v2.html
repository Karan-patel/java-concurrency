Section 01

Java Memory Model

The JMM is the contract between your Java code and the hardware. Without it, every concurrent program is undefined behavior. Every thread-safety bug—visibility races, stale reads, broken double-checked locking—traces to a JMM violation. Master this first; everything else is built on top.

Why the JMM exists

Modern CPUs execute instructions out-of-order for performance. Each core has L1/L2/L3 caches—a write on Core 1 may sit in its write buffer for microseconds before reaching main memory. The compiler reorders instructions too. Without rules, a write on Thread A may never become visible to Thread B. The JMM defines the rules precisely so you don't need to understand every CPU architecture.

Happens-Before (HB): the single rule

If action A happens-before B, then A's effects (writes) are guaranteed visible when B executes. HB is transitive: A HB B and B HB C implies A HB C. The key HB edges Java guarantees:

  • Program order: Within a single thread, each statement HB the next
  • Monitor unlock HB monitor lock: Releasing a synchronized block HB any subsequent acquisition of that same lock by any thread
  • Volatile write HB volatile read: Writing a volatile field HB any subsequent read of that same field by any thread
  • Thread.start() HB thread body: All actions before t.start() are visible inside the new thread
  • Thread body HB Thread.join(): All actions in thread T are visible to a thread that returns from T.join()
  • Static initializer HB first class use: Class loading is atomic; the static block HB any first access
  • final field write HB constructor return: A final field written in a constructor is visible to any thread that receives a properly published reference to that object
Java
// WITHOUT HB: visibility bug — thread B may spin forever
class BrokenVisibility {
    boolean flag = false;  // plain field, no HB guarantee
    int data  = 0;

    void writer() {         // Thread A
        data = 42;          // write 1
        flag = true;        // write 2 — CPU may reorder this BEFORE data=42!
    }

    void reader() {         // Thread B
        while (!flag) {}    // may loop forever (stale CPU cache)
        // Even if flag=true is seen, data might still be 0 (no HB between writes and reads)
        System.out.println(data);  // prints 0 or 42 — undefined!
    }
}

// WITH HB via volatile: volatile write HB volatile read → data=42 is always visible
class Fixed {
    volatile boolean flag = false;  // volatile establishes HB
    int data = 0;

    void writer() {
        data = 42;          // 1. plain write — program order → HB volatile write below
        flag = true;        // 2. volatile write — HB all subsequent flag reads
    }

    void reader() {
        while (!flag) {}    // volatile read — once flag=true is seen...
        // HB chain: data=42 (HB) flag=true (volatile write HB volatile read) → data=42 visible
        System.out.println(data);  // guaranteed: always prints 42
    }
}

Safe publication — publishing objects to other threads

An object is safely published when any thread that can see the reference is guaranteed to see the object's fully-initialized state. Without safe publication, you can observe a non-null reference to a partially-constructed object — one of the most dangerous bugs because it happens rarely and non-deterministically in production.

Java — Safe publication patterns
// UNSAFE: field assigned in constructor, but reference may escape before constructor finishes
class Holder {
    int value;
    Holder(int v) { this.value = v; }
}
static Holder holder;
// Thread A: holder = new Holder(42);
// Thread B: if (holder != null) print(holder.value);
// Thread B can see holder != null BUT holder.value == 0 (partially constructed)
// The CPU can reorder: write reference to holder BEFORE writing holder.value

// SAFE 1: final fields — JMM guarantees full init before constructor return
class ImmutableHolder {
    final int value;         // final: any thread seeing this object sees value=42
    ImmutableHolder(int v) { this.value = v; }
}
// No synchronization needed for immutable objects published through ANY mechanism

// SAFE 2: volatile reference — write HB read, reader sees fully constructed object
volatile Holder volatileHolder;
// Thread A: volatileHolder = new Holder(42);  // volatile write publishes fully
// Thread B: if (volatileHolder != null) print(volatileHolder.value);  // safe

// SAFE 3: synchronized — lock release HB lock acquire
Holder syncHolder;
synchronized void set(Holder h) { syncHolder = h; }
synchronized Holder get() { return syncHolder; }

// SAFE 4: static initializer — class loader is single-threaded, guaranteed
static final Holder STATIC_HOLDER = new Holder(42);  // init before any use

// SAFE 5: AtomicReference
AtomicReference<Holder> atomicHolder = new AtomicReference<>();
atomicHolder.set(new Holder(42));  // set() uses volatile write semantics

Section 02

synchronized & Intrinsic Monitors

Every Java object is a monitor. synchronized provides mutual exclusion, visibility, and ordering in one primitive. Understanding its internal implementation — from biased locking to fat locks — tells you exactly what you pay for and when.

How the monitor works internally

Internal Structure

Object header: Every object has a 64-bit mark word in its header containing lock state, GC age, identity hash code, or a pointer to a monitor object.

Biased locking (Java 8–14): First thread to acquire CAS-stamps its thread ID into the mark word. Re-entry is a single compare — no atomic operation. Revoked when contention is first detected.

Thin lock (lightweight): On first contention, JVM CAS-swaps to a pointer to a stack-allocated lock record. Second thread spins briefly. Fast when contention is low and brief.

Fat lock (inflated): When contention persists, JVM inflates to an ObjectMonitor object on the heap. Uses OS mutex (futex on Linux). Thread enters OS wait queue — context switch cost (~5μs).

Memory barrier: MonitorExit inserts a StoreStore + StoreLoad barrier. MonitorEnter inserts a LoadLoad + LoadStore barrier. This is why synchronized gives you visibility for free.

Java — synchronized anatomy
class Account {
    private long balance;
    // Use private lock object — prevents external code from accidentally locking on 'this'
    // and disrupting your synchronization. Also allows you to change lock strategy later.
    private final Object lock = new Object();

    // Instance method sync: locks on 'this' — any caller can synchronized(account) and interfere
    public synchronized void depositUnsafe(long amount) { balance += amount; }  // avoid

    // Preferred: explicit private lock — fully encapsulated
    public void deposit(long amount) {
        synchronized (lock) {            // acquires monitor on 'lock' object
            balance += amount;           // mutual exclusion + visibility guaranteed
        }                                // MonitorExit: flushes all writes to shared memory
    }

    // Static synchronized: locks on Account.class — shared across ALL instances!
    // Use only for class-level state, never for per-instance state
    private static int instanceCount = 0;
    public static synchronized void incrementCount() { instanceCount++; }

    // Reentrancy: a thread can re-acquire a lock it already holds — counter incremented
    // Lock released only when outermost synchronized block exits (counter reaches 0)
    public synchronized void outer() {
        inner();  // calls synchronized method — same thread, no deadlock
    }
    public synchronized void inner() {
        // re-entered: hold count = 2. Exits: hold count back to 1, then 0 → released.
    }
}

// Deadlock: always acquire locks in the same canonical order
// Thread A: lock(a1) → lock(a2) | Thread B: lock(a2) → lock(a1) = circular wait = DEADLOCK
void transfer(Account from, Account to, long amount) {
    // Canonical order by identity hash — consistent across all threads, no deadlock
    Object first  = System.identityHashCode(from) <= System.identityHashCode(to) ? from : to;
    Object second = first == from ? to : from;
    synchronized (first) {
        synchronized (second) {
            from.balance -= amount;
            to.balance   += amount;
        }
    }
}

// Common mistakes:
synchronized (new Object()) {}    // WRONG: new object each call = no mutual exclusion!
private Object lock = new Object();
synchronized (lock) { lock = new Object(); }  // WRONG: lock object changes → exclusion breaks!

wait / notify / notifyAll — the condition mechanism

wait(), notify(), and notifyAll() are the only way to do conditional waiting inside a synchronized block. They must be called while holding the monitor. wait() atomically releases the lock and suspends the thread. When re-awakened, it re-acquires the lock before returning.

Java — Bounded buffer using wait/notifyAll
class BoundedBuffer<T> {
    private final Object[] buf;
    private int head, tail, count;

    BoundedBuffer(int capacity) { buf = new Object[capacity]; }

    // ALWAYS use while(!condition) — NEVER if(!condition). Two reasons:
    // 1. Spurious wakeups: POSIX/Linux explicitly allows threads to wake without notify()
    // 2. notifyAll() wakes ALL waiters — only some can proceed. Others must re-check and re-wait.
    public synchronized void put(T item) throws InterruptedException {
        while (count == buf.length) {
            wait();       // atomically: releases lock + suspends thread
        }                 // on wakeup: re-acquires lock THEN re-checks condition
        buf[tail] = item;
        tail = (tail + 1) % buf.length;
        count++;
        notifyAll();      // wake ALL threads — both putters and takers re-check their condition
        // notifyAll() is almost always safer than notify()
        // notify() is ONLY correct when: all waiters are IDENTICAL type AND one proceeding
        //   is guaranteed to make progress. Violate either → missed wakeups or livelock.
    }

    @SuppressWarnings("unchecked")
    public synchronized T take() throws InterruptedException {
        while (count == 0) wait();
        T item = (T) buf[head];
        buf[head] = null;  // help GC
        head = (head + 1) % buf.length;
        count--;
        notifyAll();
        return item;
    }
}
// Problem: notifyAll() wakes BOTH putters AND takers even though each only needs to wake
// the other type. Under high load: O(N) wasteful wakeups per operation.
// Solution: ReentrantLock with two Conditions (see section 04) eliminates this.
synchronized strengths
  • Simplest correct concurrency tool
  • JVM-optimized (biased locking, thin lock)
  • Visibility guaranteed for free
  • Reentrancy built in

synchronized limits

volatile — Precise Semantics

volatile is the lightest concurrency tool. It is commonly misunderstood — both overused (treating it as a cheaper synchronized) and underused (ignoring its ordering guarantees). Understanding its exact guarantees and gaps prevents an entire class of bugs.

Exactly what volatile provides

Guaranteevolatile provides?Details
VisibilityYesWrite is immediately visible to all threads. No CPU cache staleness. Every read goes to memory (no register caching).
Ordering (happens-before)YesVolatile write HB any subsequent volatile read of the same field. All writes BEFORE the volatile write are also visible after the volatile read (program order + transitivity).
Atomicity of single accessYesReading or writing the field is atomic — even for long and double (which are otherwise 2× 32-bit ops on 32-bit JVMs).
Compound operation atomicityNocount++ is READ + INCREMENT + WRITE — three separate ops. Two threads can both read 5, both compute 6, both write 6 → lost update.
Mutual exclusionNoMultiple threads can be in a volatile-read/write block simultaneously. No atomicity across multiple fields.
Common misconception corrected: volatile does NOT just provide visibility. It also prevents reordering around the access — the JVM inserts StoreStore + StoreLoad barriers on volatile writes. The count++ bug is NOT an ordering problem — within one thread, the three steps are always ordered. It's a compound atomicity problem: two threads interleave between the three steps.
Java — volatile correct and incorrect uses
// ✓ CORRECT: single-writer flag — only one thread writes, many read
volatile boolean shutdown = false;
// Producer: shutdown = true;  (single volatile write)
// Consumers: while (!shutdown) { ... }  (volatile reads — always see latest value)

// ✓ CORRECT: published reference — single write, many reads
volatile Config config;
// Writer: config = new Config(newSettings);    // single reference swap — atomic + visible
// Readers: config.getSetting("key")            // see fully constructed Config (not partial)
// WHY safe: volatile write HB → volatile read → all Config fields visible

// ✓ CORRECT: long/double atomicity — without volatile, 64-bit writes are TWO 32-bit ops
// On 32-bit JVMs, reading/writing long/double without volatile = torn reads possible
volatile long timestamp;   // guaranteed atomic read/write on all JVMs

// ✗ BROKEN: check-then-act — even with volatile, this is a race condition
volatile boolean initialized = false;
void init() {
    if (!initialized) {     // Thread A reads false
                            // Thread B reads false (both pass this check!)
        doInit();           // both initialize → double initialization
        initialized = true;
    }
}
// Fix: synchronized or AtomicBoolean.compareAndSet(false, true)

// ✗ BROKEN: compound operations
volatile int counter = 0;
counter++;  // Thread A: read(0) → +1 → write(1)
            // Thread B: read(0) → +1 → write(1)  ← both read 0, both write 1 → lost update
// Fix: AtomicInteger, or synchronized block

// ✗ BROKEN: multi-variable invariant
volatile int min = 0;
volatile int max = 100;
// Another thread may read min=50 (new) and max=100 (old) — invariant min<=max broken mid-update
// Fix: synchronize both writes AND reads together, or use a single volatile reference to an
//      immutable Range object that encapsulates both values

// ✓ CORRECT: Double-checked locking — volatile is MANDATORY on the instance field
// Without volatile: JIT may reorder constructor body AFTER reference write → another thread
// sees non-null reference to partially constructed Singleton
class Singleton {
    private static volatile Singleton instance;  // volatile required!

    public static Singleton get() {
        if (instance == null) {                  // first check — no lock (fast path)
            synchronized (Singleton.class) {
                if (instance == null)            // second check — under lock
                    instance = new Singleton();  // volatile write: constructor body HB reference write
            }
        }
        return instance;
    }
    // Best alternative: initialization-on-demand holder (zero overhead, no volatile needed)
    private static class Holder { static final Singleton INST = new Singleton(); }
    public static Singleton getInstance() { return Holder.INST; }
}
Use volatile when
  • Single-write, multi-read flag (shutdown, initialized)
  • Publishing an immutable object reference atomically
  • Protecting a long/double for atomicity on 32-bit JVMs
  • DCL pattern — on the instance field only
  • State visible to all threads via a single non-compound write
Do NOT use volatile when
  • Multiple threads write (compound ops: ++, +=, CAS patterns) → use Atomic*
  • Multi-variable invariant must be atomic → use synchronized
  • Read-modify-write operations → use synchronized or AtomicInteger
  • You need check-then-act atomicity → use synchronized

Section 04

ReentrantLock & Conditions

ReentrantLock is synchronized with a richer API. Use it when you need: multiple wait conditions (wake only putters, or only takers), timed or interruptible lock acquisition, or explicit fairness. The key insight is that two Condition objects per lock eliminate the thundering herd problem that synchronized's single wait-set creates.

How ReentrantLock works internally

Internal Structure — AbstractQueuedSynchronizer (AQS)

AQS backbone: ReentrantLock uses AQS — a framework for building synchronizers. At its core: a single volatile int state and a CLH-variant queue of waiting threads.

State: 0 = unlocked. >0 = locked; value = hold count (reentrancy depth). Updated via CAS.

Fast path: lock() does a CAS on state (0 → 1). If it wins, thread is the holder. No OS call.

Slow path: CAS fails → thread added to AQS queue as a Node. Parks via LockSupport.park() (OS futex). Unparked when the holder calls unlock().

Fairness: Fair mode: next thread in queue always gets the lock (strict FIFO, no barging). Unfair mode: a thread calling lock() first tries a CAS before queuing — may barge ahead of waiting threads. Unfair is ~30% higher throughput (avoids context switch for the common uncontended case).

Condition: Each newCondition() creates a ConditionObject with its own internal queue. await() moves the thread from the lock's AQS queue to the condition's queue. signal() moves exactly one thread back.

Java — ReentrantLock vs synchronized — key differences
// synchronized has ONE wait-set per object. notifyAll() wakes EVERY thread.
// Under load with N putters + N takers: every put/take wakes 2N threads → O(N) wasted wakeups.

// ReentrantLock + two Conditions: signal EXACTLY the right type of waiter. Always O(1).
class SmartBuffer<T> {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();  // wait-set for PUTTERS only
    private final Condition notEmpty = lock.newCondition();  // wait-set for TAKERS only
    private final ArrayDeque<T> buf;
    private final int capacity;

    SmartBuffer(int cap) { this.buf = new ArrayDeque<>(); this.capacity = cap; }

    public void put(T item) throws InterruptedException {
        lock.lock();
        try {
            while (buf.size() == capacity)
                notFull.await();   // only putters wait here — takers never in this queue
            buf.addLast(item);
            notEmpty.signal();     // wake EXACTLY ONE taker — not all putters too
        } finally {
            lock.unlock();         // ALWAYS in finally — prevents lock leak on exception
        }
    }

    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (buf.isEmpty())
                notEmpty.await();  // only takers wait here — putters never in this queue
            T item = buf.removeFirst();
            notFull.signal();      // wake EXACTLY ONE putter
            return item;
        } finally { lock.unlock(); }
    }
}

// synchronized + notifyAll(): 16 wakeups per operation, 15 immediately re-sleep
// ReentrantLock + 2 Conditions: 1 wakeup per operation. Measured 3–5× throughput.

// tryLock() — non-blocking acquire: useful for deadlock avoidance
ReentrantLock lockA = new ReentrantLock();
ReentrantLock lockB = new ReentrantLock();

boolean transfer(Account from, Account to, long amount) throws InterruptedException {
    long backoff = 10;
    for (int attempt = 0; attempt < 10; attempt++) {
        boolean gotA = false, gotB = false;
        try {
            gotA = from.lock.tryLock(50, TimeUnit.MILLISECONDS);
            gotB = to.lock.tryLock(50, TimeUnit.MILLISECONDS);
            if (gotA && gotB) {
                from.balance -= amount;
                to.balance   += amount;
                return true;
            }
        } finally {
            // Always release in finally, in reverse order of acquisition
            if (gotB) to.lock.unlock();
            if (gotA) from.lock.unlock();
        }
        // Jitter: prevents two threads livelocking in perfect synchrony
        // Without jitter: both retry at T+100ms, T+300ms, T+700ms — always collide
        // With jitter: Thread A retries at T+123ms, Thread B at T+87ms — one gets ahead
        Thread.sleep(backoff + ThreadLocalRandom.current().nextLong(backoff / 2));
        backoff = Math.min(backoff * 2, 500);
    }
    throw new RuntimeException("Transfer failed after 10 attempts");
}

Section 05

ReadWriteLock & StampedLock

When reads heavily outnumber writes, a single exclusive lock wastes concurrency — readers could safely run in parallel. ReadWriteLock and StampedLock exploit this by separating read and write paths. The trade-off is complexity. StampedLock adds optimistic reads — the fastest possible read path, but with a retry mechanism.

ReentrantReadWriteLock

Internal Structure

State encoding: One AQS int state encodes both read and write counts. Upper 16 bits = shared read count. Lower 16 bits = exclusive write hold count.

Read lock: Multiple threads can hold it simultaneously. CAS-increment the upper 16 bits. If a writer holds the lock or a writer is queued (write preference), readers queue up.

Write lock: Exclusive. CAS on the full state to set write hold count = 1. Must wait for all readers to release.

No read → write upgrade: You cannot upgrade from read lock to write lock atomically. Must release read lock first, then acquire write lock — another writer may step in between.

Java — ReentrantReadWriteLock
class ConfigRegistry {
    private final ReentrantReadWriteLock rwl = new ReentrantReadWriteLock();
    private final Lock readLock  = rwl.readLock();
    private final Lock writeLock = rwl.writeLock();
    private Map<String, String> config = new ConcurrentHashMap<>();

    // Many readers simultaneously — no blocking between readers, only readers vs writers
    public String get(String key) {
        readLock.lock();
        try { return config.get(key); }
        finally { readLock.unlock(); }
    }

    // Exclusive write — blocks all readers AND other writers
    public void reload(Map<String, String> fresh) {
        writeLock.lock();
        try { config = new ConcurrentHashMap<>(fresh); }
        finally { writeLock.unlock(); }
    }

    // Read → compute → write: NOT atomic. Must release read, re-acquire write.
    // Another writer may step in between and change the value you just read!
    // Always re-check the condition under write lock.
    public String getOrCompute(String key, Supplier<String> loader) {
        readLock.lock();
        try {
            String v = config.get(key);
            if (v != null) return v;     // fast path: found under read lock
        } finally { readLock.unlock(); }

        // Gap here — another thread might compute and put the same key
        writeLock.lock();
        try {
            // Re-check under write lock: avoid double computation
            return config.computeIfAbsent(key, k -> loader.get());
        } finally { writeLock.unlock(); }
    }
}

// This allows you to update then immediately continue reading without another writer stepping in

StampedLock — optimistic reads

Internal Structure

Stamp: A long returned by every lock operation. Encodes mode and a version counter. Acts as both a lock receipt and a version check.

Optimistic read: tryOptimisticRead() returns a stamp WITHOUT acquiring any lock — it just records the current version. Read your data. Then validate(stamp) — if no write occurred since the stamp was taken, the stamp is still valid. If invalid, fall back to a real read lock.

Version counter: Every write increments the version bits in the state. validate(stamp) checks whether the version matches the one captured at optimistic-read time.

NOT reentrant: Unlike ReentrantLock, StampedLock is not reentrant. Calling writeLock() while already holding a write lock deadlocks. This is the #1 gotcha.

Java — StampedLock with optimistic reads
class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    // OPTIMISTIC READ — the hot path (no lock acquired at all)
    // Best-case: zero synchronization overhead on readers
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();    // records current version, no lock
        double cx = x, cy = y;                  // read values — MAY be stale if writer runs here
        if (!sl.validate(stamp)) {              // did any write happen between tryOptimistic and now?
            // Yes — our snapshot may be inconsistent. Fall back to real read lock.
            stamp = sl.readLock();
            try { cx = x; cy = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(cx, cy);  // work with consistent snapshot
    }

    // WRITE LOCK — exclusive
    void move(double dx, double dy) {
        long stamp = sl.writeLock();
        try { x += dx; y += dy; }
        finally { sl.unlockWrite(stamp); }
    }

    // LOCK CONVERSION: write → read (downgrade after write, before other writers can run)
    double updateAndGet(double newX, double newY) {

            stamp = sl.tryConvertToReadLock(stamp);
            return Math.hypot(x, y);
        } finally { sl.unlock(stamp); }
    }

Atomic Operations & CAS

Compare-And-Swap (CAS) is the hardware primitive that makes lock-free programming possible. No OS mutex, no context switch — a single CPU instruction. Understanding CAS means understanding how all of java.util.concurrent's non-blocking machinery works internally.

CAS: the hardware primitive

CAS is a single CPU instruction: LOCK CMPXCHG on x86. Semantics: "If memory[addr] == expected, atomically write desired and return true. Otherwise leave unchanged and return false." The key: it's atomic at the hardware level — no OS, no lock, no context switch.

Java — CAS mechanics
// AtomicInteger.incrementAndGet() — this is what happens under the hood:
public final int incrementAndGet() {
    for (;;) {
        int current = get();             // volatile read: current value
        int next    = current + 1;       // desired: current + 1
        if (compareAndSet(current, next)) // CAS: atomic if current hasn't changed
            return next;
        // CAS failed: another thread changed the value between our read and CAS
        // Spin and retry — this is the CAS loop pattern
    }
}
// Why this is correct: if CAS succeeds, we know no other thread modified the value
// between our read and our write. The increment is effectively atomic.
// Cost: under low contention, 1 CAS. Under high contention, multiple retries (spin).

// Custom CAS loop: track running maximum without any lock
AtomicLong maxSeen = new AtomicLong(Long.MIN_VALUE);
void observeValue(long v) {
    long cur;
    do {
        cur = maxSeen.get();
        if (v <= cur) return;   // short-circuit: already larger than v
    } while (!maxSeen.compareAndSet(cur, v));
    // If CAS fails: another thread updated maxSeen — re-read and re-check
}
// Java 9+ cleaner form:
maxSeen.updateAndGet(cur -> Math.max(cur, v));

LongAdder vs AtomicLong — the contention difference

LongAdder Internal Structure

AtomicLong under high contention: All threads CAS on ONE volatile long at ONE memory address. With 16 threads: each CAS fails 15/16 of the time on average. Cache line bouncing between CPUs via MESI protocol. Effective throughput degrades linearly with thread count.

LongAdder strategy: One base volatile long + a dynamic array of Cell objects. Under low contention, threads CAS on base (same as AtomicLong). Under contention, threads hash to their own Cell and update it. sum() merges base + all cells. Result: near-zero contention under any load — each thread mostly updates its own cache line.

Trade-off: sum() is not a point-in-time snapshot — cells can be updated between reads. Use AtomicLong when you need exact current value for CAS decisions; use LongAdder for high-frequency counters and metrics.

ConcurrentHashMap

The most important concurrent data structure in Java. Understanding its internals — three write paths, bucket-level locking, tree conversion, and LongAdder-style counting — lets you use it precisely and diagnose performance issues confidently.

Java 8+ internal structure

Internal Structure (Java 8+)

Backing array: A volatile Node[] table. Each index is a bucket. Starts at 16 buckets, doubles on resize (load factor 0.75).

Bucket states: null (empty), Node (linked list head), TreeBin (red-black tree root), ForwardingNode (resize in progress).

Lock granularity: synchronized(bucketHead) — one lock per non-empty bucket. Max parallelism ≈ table length. Under a 256-bucket table: 256 independent operations can proceed simultaneously.

Tree conversion: When a linked list reaches 8 nodes, it converts to a TreeBin (red-black tree). O(n) worst-case becomes O(log n). Converts back when size drops to 6. Requires table ≥ 64 elements; otherwise the table is resized instead.

Size tracking: volatile baseCount + CounterCell[] array (LongAdder pattern). Each thread updates its own CounterCell. mappingCount() sums all cells. No global lock for counting.

CopyOnWrite Collections

CopyOnWriteArrayList and CopyOnWriteArraySet implement an extreme trade-off: reads are completely lock-free at all times (even during writes), but every write creates a full copy of the backing array. Correct in exactly one scenario. Catastrophic in every other.

How it works internally

Internal Structure

Backing array: A volatile Object[] array reference. Reads always go directly to the current array — no locking ever.

Write path: One ReentrantLock (write lock). On any mutation: Arrays.copyOf(array, len+1) → mutate the copy → setArray(newArray) (volatile write). The volatile write makes the new array atomically visible to all readers.

Iteration snapshot: The iterator captures the array reference at creation time. Iterating while another thread mutates is safe — you see the old snapshot. No ConcurrentModificationException ever. But you may not see the latest additions.

Cost formula: Each write = O(n) time + O(n) memory (full array copy). For n=1000 elements at 100 writes/sec = 100,000 element copies per second + GC pressure from discarded arrays.

Java — CopyOnWriteArrayList mechanics and correct use
// Read path — zero synchronization, fastest possible
public E get(int index) {
    return elementAt(getArray(), index);  // just: volatile read of array reference, then array[index]
}                                          // No lock. No CAS. Maximum concurrency.

// Write path — O(n) copy
public boolean add(E e) {
    final ReentrantLock lock = this.lock;
    lock.lock();
    try {
        Object[] elements    = getArray();
        int len              = elements.length;
        Object[] newElements = Arrays.copyOf(elements, len + 1);  // FULL COPY — O(n) time + memory
        newElements[len]     = e;
        setArray(newElements);            // volatile write — atomically visible to all readers
        return true;
    } finally { lock.unlock(); }
}

Lock-Free Queues: ConcurrentLinkedQueue & Deque

The Michael-Scott algorithm implements a lock-free FIFO queue using only CAS. No thread ever blocks waiting for another — the crucial property for systems where blocking is unacceptable. Understanding cooperative progress — where threads help each other complete partial operations — is the key insight.

ConcurrentLinkedQueue internals

Michael-Scott Queue Structure

Structure: Singly-linked list of Node objects. Two AtomicReference fields: head (for dequeue) and tail (for enqueue). Head and tail are "lazy" — they may lag one step behind the true head/tail.

Enqueue: Two CAS operations. (1) CAS on tail.next to link the new node. (2) CAS on tail to advance it. Step (2) is best-effort — another thread can do it. This is the cooperative completion property: any thread that sees tail.next != null will help advance tail before proceeding.

Dequeue: CAS on head to advance it, returning the old head's item. If head == tail and head.next == null, queue is empty. If head == tail but head.next != null, tail is lagging — help advance it.

size() is O(n): There is no atomic size counter — counting requires traversing the entire linked list. Never call size() in production; use isEmpty() instead.

Java — ConcurrentLinkedQueue: when to use and gotchas

Blocking Queues — The Complete Picture

BlockingQueue is the standard implementation of the producer-consumer pattern. put()/take() encapsulate all wait/notifyAll complexity behind a clean API. Choosing the right type shapes your system's throughput, memory profile, and backpressure behavior.

ArrayBlockingQueue vs LinkedBlockingQueue internals

ABQ: Single Lock + Circular Array

Structure: Pre-allocated Object[] array. Three int fields: head (take index), tail (put index), count. One ReentrantLock for both put AND take. Two Conditions: notEmpty (takers wait here), notFull (putters wait here).

Implication: A put() and a take() happening simultaneously must contend on the same lock — even though they access different ends of the array. This is the throughput ceiling: put and take are serialized against each other.

Memory: Fixed at construction. No GC churn. Predictable. Good for memory-constrained environments.

LBQ: Two Locks + Linked Nodes

Structure: Singly-linked list of Node objects. Two ReentrantLocks: putLock (tail end) and takeLock (head end). One AtomicInteger count (updated from both locks). Two Conditions: one per lock.

Key advantage: A put() and a take() happening simultaneously acquire DIFFERENT locks — they never contend each other. Producers and consumers run in parallel. This is why LBQ has higher throughput under load.

Cost: Each put() allocates a new Node object — GC pressure. Default capacity is Integer.MAX_VALUE — effectively unbounded unless you specify a capacity.

Java — API, selection, and production patterns

ConcurrentSkipListMap & Set

The only concurrent sorted collection in the JDK. Lock-free for reads and writes, maintains sorted order automatically, and provides the full NavigableMap API including range queries. The go-to for leaderboards, time-series indexes, and ordered event queues.

Skip list internals

Internal Structure

Skip list: A probabilistic data structure. A sorted linked list at the bottom (Level 1). Each node is independently promoted to higher "express lane" levels with probability p (typically 0.25). At Level k: only ~n × 0.25^k nodes exist.

Search: Start at the highest level. Skip across large chunks. Descend a level when you overshoot. Expected O(log n) — provable with high probability.

Lock-free writes: Each node's next pointers are AtomicReference. Insert: find the position at each level, CAS-link the new node bottom-up. Delete: CAS-mark the node as deleted (a special "marker" node), then unlink lazily. Any thread that encounters a deleted node helps unlink it (cooperative progress).

Memory cost: Each node has 1–4 next pointers on average (random levels). ~3× memory vs a HashMap entry. Factor this into capacity planning for large maps.

Thread Pools & ExecutorService

Thread creation costs ~1ms and ~1MB stack. Pools amortize this. ThreadPoolExecutor is the engine — every Executors.newXxx() is a shortcut with hidden dangerous defaults. In production you always construct ThreadPoolExecutor directly and size it from measured data, not guesses.

ThreadPoolExecutor: full control surface

Submission lifecycle — the critical subtlety

Step 1 — below corePoolSize? Create a new core thread immediately, even if idle threads exist. Core threads stay alive indefinitely.

Step 2 — at corePoolSize, queue not full? Enqueue the task. DO NOT create new threads yet. This surprises engineers: max threads are NOT created when the pool is at core capacity — only when the QUEUE is full.

Step 3 — queue full, below maximumPoolSize? Create a non-core thread. Non-core threads die after keepAliveTime of idle time.

Step 4 — queue full, at maximumPoolSize? Rejection handler fires. This is your backpressure signal.

Futures & CompletableFuture

CompletableFuture is non-blocking async composition. The calling thread registers a continuation and moves on — it never blocks waiting for a result. The difference between blocking a thread per request and freeing it is the difference between 100 and 100,000 concurrent requests on the same hardware.

Fork/Join Framework

Divide-and-conquer parallelism with work-stealing. ForkJoinPool eliminates the central queue bottleneck by giving each thread its own work deque and letting idle threads steal from busy ones. This is the engine behind parallel streams and the right tool for CPU-bound recursive algorithms.

Work-stealing: why it scales

Work-Stealing Architecture

Per-thread WorkQueue: Each worker thread has its own double-ended deque. Own tasks: pushed to the TOP (LIFO — exploits temporal locality, recently-created tasks tend to be related).

Stealing: Idle threads steal from the BOTTOM of other threads' deques (FIFO — steals the oldest, largest chunk of work). The producer pushes/pops from the top; the stealer pops from the bottom — minimal contention between owner and stealer, near-zero between stealers since they target different victim queues.

No central queue: Eliminates the global lock bottleneck that throttles ThreadPoolExecutor at high task rates. Scales near-linearly with core count for recursive workloads.

Join optimization: When a thread calls fork(), the task goes to its own queue. When it calls join() on a forked task that hasn't started, it may execute the task itself (work inlining) — avoids the overhead of scheduling and waking another thread.

Java — RecursiveTask and threshold tuning
class ParallelSum extends RecursiveTask<Long> {
    // THRESHOLD TUNING is the most important variable.
    // Too small: task creation overhead dominates (each task has ~500ns overhead)
    // Too large: poor parallelism — some threads idle while others grind
    // Target: base case execution ~0.5–1ms. For arrays: data_size / (N_cpus × 4) is a starting point.
    private static final int THRESHOLD = 10_000;
    private final long[] data;
    private final int from, to;

    @Override
    protected Long compute() {
        if (to - from <= THRESHOLD) {
            long sum = 0;
            for (int i = from; i < to; i++) sum += data[i];  // sequential base case
            return sum;
        }
        int mid = (from + to) >>> 1;  // unsigned right shift avoids integer overflow
        ParallelSum left  = new ParallelSum(data, from, mid);
        ParallelSum right = new ParallelSum(data, mid, to);

        left.fork();                     // push left to THIS thread's deque (async)
        long rightResult = right.compute();  // compute right inline — no context switch
        long leftResult  = left.join();      // wait for left: may execute it inline if not stolen
        // KEY: always fork() the left, compute() the right inline.
        // This way the thread always has useful work (right task) while waiting for the fork.

        return leftResult + rightResult;
    }
}

Java — RecursiveAction and parallel streams
// RecursiveAction: no return value — for parallel array modification, sorting, filling
class ParallelFill extends RecursiveAction {
    private static final int THRESHOLD = 50_000;
    @Override protected void compute() {
        if (to - from <= THRESHOLD) {
            Arrays.fill(data, from, to, value);  // sequential
            return;
        }
        int mid = (from + to) >>> 1;
        invokeAll(                               // fork BOTH subtasks simultaneously and join both
            new ParallelFill(data, from, mid, value),
            new ParallelFill(data, mid, to, value)
        );
        // invokeAll() is equivalent to: left.fork(); right.compute(); left.join();
        // but cleaner when you have symmetric subtasks with no value to return
    }
}

Virtual Threads (Java 21)

Project Loom solves the C10K problem permanently. Virtual threads decouple application concurrency from OS threads. For I/O-bound work, you write simple blocking code and get non-blocking scalability automatically. This makes most of the reactive complexity in Sections 12–14 optional for I/O-bound services.

Platform vs virtual threads

How virtual threads work

Carrier threads: A small ForkJoinPool of platform threads (typically N_cpus). Virtual threads are mounted onto a carrier to execute, unmounted when blocking.

On block: VT calls blocking I/O (socket read, sleep, lock). JVM intercepts at the java.* layer. Saves the VT's call stack to the heap (~few KB). Unmounts VT from carrier. Carrier is immediately free to run another VT. When I/O completes, JVM re-mounts the VT on any available carrier.

Stack on heap: VT stack is a growable heap object (few KB). Platform thread stack is OS-allocated memory (512KB–1MB fixed). This is why millions of VTs are feasible — the heap scales; OS threads don't.

Cost: Creation ~1μs (vs ~1ms for platform thread). Stack ~few KB (vs ~1MB). Blocking: JVM operation (~50ns) vs OS context switch (~5μs). 1000× cheaper to create, 100× cheaper to block.

Concurrency Design Patterns

Patterns are recurring solutions to recurring problems. Each names a design intent precisely — "active object," "half-sync/half-async," "two-phase termination" — so architects can communicate designs without re-explaining the full structure. These are the vocabulary of concurrent system design.

Producer-Consumer

Decouple production rate from consumption rate via a shared bounded buffer. The buffer provides natural backpressure: a full buffer slows producers. An empty buffer blocks consumers. This IS BlockingQueue's contract.

Java — production-grade producer-consumer
BlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000);
static final Task POISON  = new Task("__stop__");

// Producers: naturally throttled by put() blocking on full queue
ExecutorService producers = Executors.newFixedThreadPool(3);
AtomicBoolean done = new AtomicBoolean(false);
producers.submit(() -> {
    try {
        while (!done.get()) { queue.put(source.next()); }
        for (int i = 0; i < NUM_CONSUMERS; i++) queue.put(POISON);  // one pill per consumer
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
});

// Consumers: each exits on its own poison pill
ExecutorService consumers = Executors.newFixedThreadPool(5);
for (int i = 0; i < 5; i++) {
    consumers.submit(() -> {
        try {
            while (true) {
                Task t = queue.take();
                if (t == POISON) return;
                process(t);
            }
        } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    });
}

Active Object

Each object owns a private thread and a private mailbox. All public methods post messages to the mailbox. The private thread processes one message at a time. Zero locks within the object — sequential execution per entity, maximum parallelism across entities. Akka actors, Go goroutines with channels, and Erlang processes all implement this pattern.

Java — Active Object (per-account actor)
class ActiveAccount {
    private final BlockingQueue<Runnable> mailbox = new LinkedBlockingQueue<>();
    private long balance;

    ActiveAccount(long initial) {
        this.balance = initial;
        Thread actor = new Thread(() -> {
            while (true) {
                try { mailbox.take().run(); }  // process one message at a time — no locks needed
                catch (InterruptedException e) { Thread.currentThread().interrupt(); break; }
            }
        }, "account-actor");
        actor.setDaemon(true);
        actor.start();
    }

    // All methods are async messages — non-blocking to callers
    public CompletableFuture<Long> getBalance() {
        CompletableFuture<Long> f = new CompletableFuture<>();
        mailbox.offer(() -> f.complete(balance));
        return f;
    }
    public void deposit(long amount)  { mailbox.offer(() -> balance += amount); }
    public void withdraw(long amount) { mailbox.offer(() -> {
        if (balance >= amount) balance -= amount;
        else throw new RuntimeException("Insufficient funds: " + balance);
    }); }
}
// Zero synchronized, zero Lock — yet perfectly thread-safe.
// 1000 accounts = 1000 actors = fully parallel across accounts, sequential within each.

Two-Phase Termination

Phase 1: set termination flag, interrupt if blocked. Phase 2: thread completes current work and cleans up before dying. Never use Thread.stop() — it leaves locks unreleased and objects in inconsistent state.

Java
class FlushWorker {
    private Thread worker;
    private volatile boolean terminating = false;

    void start() {
        worker = new Thread(() -> {
            while (!terminating && !Thread.interrupted()) {
                try { flushPendingWrites(); }
                catch (InterruptedException e) {
                    Thread.currentThread().interrupt();  // restore interrupt flag
                    break;
                }
            }
            // Phase 2: guarantee cleanup — runs even after interrupt
            drainAndFlushAll();
            log.info("Flusher stopped cleanly");
        }, "flush-worker");
        worker.setDaemon(false);  // non-daemon: JVM waits for it on shutdown
        worker.start();
    }

    void stop() throws InterruptedException {
        terminating = true;       // Phase 1a: signal
        worker.interrupt();       // Phase 1b: interrupt if blocked on I/O or sleep
        worker.join(5_000);       // wait up to 5s for Phase 2 to complete
        if (worker.isAlive()) log.warn("Worker did not stop cleanly within 5s");
    }
}

Half-Sync / Half-Async

Two layers: async I/O layer (single thread, event loop, non-blocking) + sync business logic layer (thread pool, blocking allowed). They communicate via a handoff queue. This is the architecture of Netty, Tomcat NIO, Node.js, and every high-performance I/O framework.

Java — Half-Sync/Half-Async
class HalfSyncServer {
    private final Selector selector;             // Async layer: 1 thread, 10k+ connections
    private final ExecutorService syncPool;      // Sync layer: blocking business logic

    void asyncEventLoop() {                      // ONE non-blocking thread handles all I/O
        while (running) {
            selector.select();
            for (SelectionKey key : selector.selectedKeys()) {
                if (key.isReadable()) {
                    byte[] data = readNonBlocking(key);  // fast: drain OS buffer
                    syncPool.submit(() -> process(data)); // hand off immediately
                }
            }
            selector.selectedKeys().clear();
        }
    }

    void process(byte[] data) {
        // Sync layer: plain blocking code — easy to write, test, and maintain
        Request  req  = parse(data);
        Response resp = service.handle(req);    // may call DB, external services, etc.
        sendResponse(resp);
    }
}
// Async layer: O(1) threads per N connections — scales to 100k connections on one thread
// Sync layer: 1 thread per concurrent in-flight request — bounded by pool size

Decision Guide — Which to Use When

Real decisions start from a scenario. The question is never "which class do I know?" — it is "what is my access pattern, concurrency level, failure mode, and performance requirement?" These answers narrow the choice to one correct answer.

The 3 primary questions

Decision framework

//   No  → volatile (single-write flag), final fields, immutable objects — no synchronization needed
//   Yes → go to Q2

//   No  (single field, single op) → AtomicInteger / AtomicLong / AtomicReference
